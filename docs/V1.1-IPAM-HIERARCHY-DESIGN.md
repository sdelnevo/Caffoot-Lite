# Caffoot Lite v1.1 — IPAM hierarchy implementation plan

Status: proposed foundation, for review before modifying production validation.

## Current constraints (verified against main)

- `app/caffoot-lite.html` stores subnets in `appState.subnets` with `id,name,cidr,vlan,gateway,description`.
- `phase12Cidr` accepts aligned IPv4 /23–/30 only; `phase12Overlap` rejects all overlapping ranges.
- `normaliseState` requires a VLAN and usable gateway for every subnet and rejects overlaps.
- `validateApplicationState` independently requires a gateway and globally unique subnet VLANs.
- `handleSubnetSubmit` also rejects overlap and requires a gateway/VLAN. The IPAM renderer assumes a host-address network, so large parents must not be displayed as address pages.
- Schema-1 backup export/import and legacy imports must remain supported; the app currently uses internal stateVersion 3.

## Proposed model

Keep the existing flat `subnets` array and stable IDs. Add optional `parentId` (ID of immediate parent; missing/null/empty means root) and `kind` (`container` or `network`; missing means legacy `network`).

A `container` reserves address space for children, and has no mandatory VLAN or gateway. It must not own IPAM/device primary addresses directly. A `network` retains existing gateway/VLAN and IP allocation behaviour. A network may have a parent, but for v1.1 we should only allow children under containers, avoiding ambiguous ownership of IPs. Multi-level containers are supported.

Example:
```json
{"id":"company","name":"Company","cidr":"10.0.0.0/8","kind":"container","parentId":null}
```
```json
{"id":"london","name":"London","cidr":"10.10.0.0/16","kind":"container","parentId":"company"}
```
```json
{"id":"servers","name":"Servers","cidr":"10.10.10.0/24","kind":"network","parentId":"london","vlan":10,"gateway":"10.10.10.1"}
```

## Validation requirements

1. Parse aligned IPv4 CIDRs using numeric interval math (no per-address enumeration). Accept /0–/32 for containers subject to explicit product limits; keep current /23–/30 for networks until a separate deliberate decision expands assignable network sizes.
2. Invalid/misaligned CIDRs must be rejected, with suggested canonical boundary; never silently rewrite.
3. Every `parentId` must resolve to another existing container, never itself. Detect cycles.
4. A child interval must be strictly contained within its parent. No equal parent/child CIDRs.
5. Two sibling children cannot overlap; unrelated roots cannot overlap. Ancestor containment is the only allowed overlap.
6. IDs and CIDRs remain unique across the inventory.
7. Prevent deleting a parent with children; reject edits that invalidate descendants or move existing IP assignments out of their owning network.
8. Network IPs must resolve to one most-specific eligible `network`; containers are not IPAM address owners.
9. Auto-split into equal CIDR blocks and manual mixed-size allocation must call the same validation path. Preview all proposed children and commit atomically, with rollback on failed persistence.
10. Large parent allocations must never trigger massive address lists or loops.

## Compatibility and rollout

- Missing `kind`/`parentId` are interpreted as a root `network` without rewriting existing IDs or CIDRs.
- Do not change the published v1.0.3 release or the existing schema-1 fixtures.
- Before shipping new hierarchical backups, explicitly decide and test whether the changed subnet semantics require schema version 2. An older v1.0.3 app cannot validate parent/child overlap; do not promise backward import compatibility from new backups into older app versions.
- Update BOTH `normaliseState` and `validateApplicationState` and the subnet edit/delete paths together; partial validation would risk invalid inventory.
- Keep firewall gateway ownership as a separate v1.1 PR: firewalls may use the gateway or a management IP; other device types may not claim the gateway; IP ownership must remain unique.
- Keep site-aware VLAN identity as a separate PR.

## Acceptance tests for implementation PR

- Existing schema-1 and legacy backup fixtures roundtrip unchanged.
- Valid /8 > /16 > /24 hierarchy; nested containers; root legacy subnet.
- Sibling overlap, duplicate CIDR, unrelated root overlap, child outside parent, missing parent, cycle, parent with wrong kind all fail.
- Boundary suggestion: 10.10.10.75/26 -> 10.10.10.64/26.
- Auto split and manual allocations reject collisions and preserve state on failed save.
- Deleting or resizing parent with children fails safely.
- Device and IPAM allocations never attach to containers.
- Offline build and existing release test suite pass, followed by browser testing.

## UI text capitalisation standard

All user-facing **button labels** and **headings** in Caffoot Lite must use **Title Case**: capitalise the first letter of each principal word, including form labels that function as section or field headings.

Examples:
- `Subnet Type` (not `Subnet type`)
- `Network Identity` (not `Network identity`)
- `Add Subnet`, `Save Subnet & VLAN`, `Cancel`

Apply this convention to new UI work and when updating existing buttons or headings. Preserve established technical abbreviations and casing, such as `IPAM`, `VLAN`, `CIDR`, and `IP`. Sentence-style explanatory text, help text, validation messages, and descriptions do not need Title Case.

## Review decision needed

Should assignable `network` CIDRs remain /23–/30 for the first foundation PR, or expand to /1–/32? Recommended: retain existing /23–/30 initially to minimise regression risk, and separately expand supported network sizes with UI and address paging tests.


## v1.1 application-wide navigation and layout design decision

Status: agreed design direction; implement incrementally on the v1.1 development branch, without changing published v1.0.3.

### Shared design language

- Use an expandable left sidebar for major application areas, including IPAM, Device Inventory, Network Racks, Change History, and Settings & Data where appropriate.
- Expand the active section to reveal clear, task-oriented sub-navigation and actions; keep navigation consistent between sections.
- Reduce redundant large navigation/action buttons in the main workspace. The main panel should prioritize useful content, selection context, and relevant details.
- Preserve a clear visual hierarchy, accessible focus states, keyboard navigation, responsive/mobile behavior, and light/dark theme parity.
- Follow the established Title Case standard for user-facing headings, field labels, and buttons.
- Keep common actions discoverable: a primary action can live in expanded navigation, with a small contextual action near the object it affects when useful.
- Do not introduce misleading or nonfunctional navigation items. Maintain existing features and paths during migration.

### IPAM-specific pattern

- The main IPAM Overview displays an expandable address-space tree: parent containers can be expanded to reveal nested containers and assignable networks.
- Selecting a network displays its gateway, VLAN, capacity, allocations, and a clear path to browse IP addresses.
- Selecting a container displays its CIDR, child ranges, and available address-space summary, not host-by-host IP lists.
- The IPAM sidebar offers Overview, IP Addresses, Manage Subnets, and Add Subnet, with the Add Subnet form available directly.
- A contextual Add Child Subnet action on a container should preselect its parent.
- Keep the existing modal form, validation, persistence, and backup contracts until replacement behavior is tested.

### Rollout and acceptance

1. Establish reusable sidebar expansion, active-section indication, and consistent main-panel patterns.
2. Implement and visually test IPAM navigation and expandable hierarchy first.
3. Extend the same patterns to Device Inventory, Network Racks, Change History, and Settings & Data in separate small changes.
4. Verify accessibility, mobile layout, keyboard operation, dark mode, regression tests, and backup roundtrips at each milestone.
5. Keep PR #25 draft and unmerged until the complete v1.1 feature has been validated.


## v1.1 terminology decision — IP Address Block

The agreed user-facing term for a hierarchical parent CIDR range is **IP Address Block**, replacing **Parent Container**. Use **IP Address Block** in the Subnet Type selector, **IP Address Block Name** for its name, **Parent IP Address Block** for its parent selector, and **Save IP Address Block** for the save action. The hierarchy should identify these objects as **IP Address Blocks**. This avoids confusion with application containers such as Docker. Maintain the internal serialized kind value `container` for backward compatibility; do not migrate existing records solely to rename the UI. The application-wide Title Case standard still applies. Existing earlier references to “container” in technical design discussions refer to this same internal type.
